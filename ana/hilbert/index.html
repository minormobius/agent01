One unbroken path through every cell of the unit tesseract cut into a grid, each step to a cell that shares a face. Cut each cell again and the path is redrawn as sixteen copies of itself, one per sub-tesseract, joined end to end. Drag to turn it; switch the drag to w to turn it ana and kata.

how it works

Number the cells along the path, 0 to 16b − 1, and write each number in base 16. The first digit says which of the tesseract's sixteen halves-of-halves-of-halves-of-halves the cell is in, the next which sixteenth of that, and so on: each digit is a step deeper. The sixteen sub-tesseracts are visited in the order the order-1 path visits the tesseract's corners, a Gray code that flips one coordinate at a time in the ruler sequence w z w y w z w x w z w y w z w, ending one step along x from where it began; each copy is turned and reflected so that it starts where the last one ended.

The coordinates come straight from the digits by John Skilling's bit tricks (Programming the Hilbert curve, 2004): a Gray decode and one sweep of reflections and exchanges, the same code for the square, the cube and the tesseract. Try 2 and 3 dimensions to calibrate your eye.

What it's for: cells near each other on the path are near each other in space, so sorting points by their place along it keeps neighbours together. That's how databases index maps and how renderers order their work. The converse fails: neighbours in space can be far apart on the path, across the seams between copies. Slide the slice and watch the path leave it and come back.

Checked: test/hilbert.selftest.mjs holds the path to visiting every cell once, stepping only to face-neighbours, starting and ending at corners one edge apart, inverting exactly, and being, at every scale, the coarser path with each cell replaced by a copy.
