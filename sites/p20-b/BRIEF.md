# take-escher — BRIEF

## The request, in the requester's words
"take Escher woodcut circle limit III and make it an interactive explorer.
Let the user pick a row of fish to "swim" or translate n The direction of
their nose and let the other fish follow as they must to preserve tiling.
Effectively, use tiling to play with a Poincaré disk hyperbolic[ tiling]."

## Acceptance checklist (built from the request)
1. Circle Limit III–inspired visual: a hyperbolic tiling of fish in a
   Poincaré disk, in the house dark palette.
2. The disk is a REAL hyperbolic tiling, generated by hyperbolic geometry
   (Möbius transforms, not a static image or a fake repeating raster).
3. The user can grab a fish/row and drag/"swim" it in a direction.
4. When one row moves, the rest of the tiling visibly follows/updates —
   because in a rigid tiling that is the only way a translation can happen
   (see DECISIONS).
5. Explicit "row" concept: clicking a fish selects the geodesic row it
   belongs to, distinctly highlighted, with dedicated swim-forward /
   swim-back controls (not just free-drag) so the "pick a row" part of the
   ask is literal, not just implied by generic panning.
6. Reset control back to the starting view.
7. Mobile-usable: viewport meta, ≥16px inputs, ≥44px tap targets, no
   horizontal scroll at 360px, pointer events (not mouse-only), motion
   respects prefers-reduced-motion (drag/step transitions become instant).
8. Honest copy: says plainly this is inspired by Circle Limit III, not a
   pixel copy, and that "rows" here are geodesics (straight in the
   hyperbolic sense) rather than Escher's actual curved fish-spines.

## Decisions
- **Chose the {8,3} hyperbolic tiling** (regular octagons, three meeting at
  each vertex) built from the ORIENTATION-PRESERVING subgroup only (edge
  half-turns + generator composition, no reflections) — this is what keeps
  every generated fish facing the same way instead of mirroring at tile
  boundaries, which is how Escher's actual fish tilings work too (he never
  mirrors a fish). Octagons were picked because 1/8+1/3 < 1/2 (genuinely
  hyperbolic) and because Circle Limit III's underlying combinatorics are
  themselves based on the {8,3} tessellation, so the choice is the closest
  honest match reachable without reproducing Escher's actual non-geodesic
  fish-spine curves.
- **Global rigid-body interpretation of "row follows row."** A regular
  hyperbolic tiling's symmetry is rigid: there is no isometry that
  translates ONE row while leaving its neighbours fixed and still tiles
  correctly — moving a row without breaking the tiling forces the SAME
  isometry onto the whole plane. So "the other fish follow as they must to
  preserve tiling" is implemented literally: dragging (or stepping) applies
  one global Möbius transform to every generated tile. This is not a
  simplification for convenience, it's the actual mathematical content of
  the request, and the UI copy says so directly rather than leaving it
  implicit.
- **Row = a geodesic axis through the tile you grabbed, aligned to one of
  the octagon's 4 edge-direction pairs** (opposite edges k and k+4 of the
  8-gon give the same axis). Clicking near a tile picks the axis nearest
  the click angle; swim +/- buttons apply a continuous hyperbolic
  translation along that axis via `diskTranslate`. Free dragging anywhere
  on the canvas does the same underlying operation (grab-any-point,
  translate to where you drag it) without requiring a row to be selected
  first, since a visitor's first instinct will be to just drag.
- **Tile generation via BFS with a hyperbolic-radius cutoff**, not a fixed
  depth, so the disk fills edge-to-edge instead of stopping at an arbitrary
  ring. Deduplicated by rounding each tile's center point — cycles around a
  vertex (3 octagons meet there) would otherwise revisit tiles and blow up
  the queue.
- **No PDS / sign-in.** The page is fully meaningful without it (pure
  client-side geometry toy) — per the kit's own "sign-in is optional unless
  the site is meaningless without it," and there's nothing here worth
  saving to a repo (no score, no persistent creative output).
- **Matrix (SU(1,1)) representation for Möbius transforms**, not chained
  closures, so composing many transforms (BFS depth + drag accumulation)
  stays numerically simple and fast to redraw every frame.

## The plan — this turn shipped all of it
Core tiling + fish rendering, free drag pan, row pick + highlight + swim

## Future turns, if requested (not built)
1. **Recentering when the drag runs out of pre-generated tiles.** The
   tiling is a fixed, finite BFS-generated set (~650 tiles, capped by
   hyperbolic radius from the origin); dragging is clamped
   (`DRAG_LIMIT = 0.965` on the transformed origin) so you can't drag past
   the edge of what's generated, but that means very large drags just stop
   rather than revealing more tiling. The real fix is HyperRogue-style
   recentering: when the effective view center drifts far from the BFS
   root, re-root the transform tree at whichever tile is now nearest
   center (`newG_i = compose(inverse(g_j), g_i)`) and extend the BFS
   outward from there — the visual position doesn't change (it's a pure
   reparameterization) but the coverage grows. Worth doing before removing
   the clamp.
2. Curved (equidistant-curve) fish spines instead of straight geodesic
   rows, to match Escher's actual line-of-flow more closely — noted as a
   deliberate simplification in the on-page copy already.
3. A visual trace of the WHOLE selected row (currently only the tapped
   fish itself is highlighted, not the chain of fish along its geodesic) —
   would need a point-to-geodesic distance test to find which generated
   tiles lie near the axis.
4. Zoom control, a fish-density/complexity slider.

## Gotchas
- The hand-derived Mobius/half-turn/hyperbolic-midpoint math worked on the
  first try — verified visually (`eyes.look`), the tiling is edge-to-edge
  with no gaps or mirrored fish, and dragging/swimming stays rigid with no
  drift. If a future edit to that math looks subtly wrong, check tile
  boundaries meeting cleanly and fish never mirroring — those are the two
  tells for a sign error in `mobHalfTurn`/`hypMidpoint`.
- **Real CSS bug, worth remembering generally**: `<div class="row" hidden>`
  did NOT hide — the page's own `.row { display: flex }` rule beat the
  browser's default `[hidden]{display:none}` because author CSS always
  wins over user-agent CSS regardless of specificity. Switching to the
  kit's `.hidden` class didn't fix it either, for the same reason one level
  up: `.hidden` and `.row` are both author-origin with equal specificity
  (one class each), and `.row` appears later in the cascade (this page's
  own `<style>` block comes after the linked `tokens.css`), so it still
  won. Fixed by adding `#swimControls.hidden { display: none; }` (ID+class
  beats class alone). **Any element that needs `hidden`/`.hidden` to work
  and also carries a class that sets its own `display` needs an explicit
  higher-specificity override** — the attribute/class alone is not enough
  once something else on the same element also declares `display`.
- `mcp__eyes__look` reloads the page fresh every call — state does not
  persist between separate `look`/`drive` invocations, only within one
  `drive` call's step list. Useful to know when testing a stateful flow.

## What was verified (via eyes tools)
- Core tiling: correct, real hyperbolic geometry — octagons meeting 3 to a
  vertex, fish shrinking smoothly toward the boundary, 8-way color pinwheel,
  no gaps/overlaps, no mirrored fish. Confirmed by screenshot.
- Free drag: grabbing anywhere and dragging moves the entire tiling
  rigidly; confirmed before/after screenshots differ correctly and the
  tiling stays intact.
- Row select + swim: tapping a fish (vs. dragging — there's a movement
  threshold to distinguish tap from drag) selects it, shows the swim
  controls and a highlighted outline; pressing swim-forward repeatedly
  visibly carries that row's fish toward/through the center while the rest
  of the pattern follows, tile for tile, exactly as the request asked.
- Reset: returns to the exact starting view and re-hides the swim
  controls.
- Mobile (390×844): disk stays a true circle (this needed a fix — see
  below), no horizontal scroll, 44px+ buttons, panel readable.
- No console errors in any of the above.

## One CSS bug fixed during build
The `#stage` was `width: 100%; aspect-ratio: 1/1; max-height: min(74vh,
640px)`, which let the max-height clamp the height independently of the
width, producing a stretched OVAL disk instead of a circle (very visible
once screenshotted, invisible from reading the CSS). Fixed by making width
itself the clamped dimension: `width: min(100%, 74vh, 640px); aspect-ratio:
1/1;`. Worth remembering for any other circular/square canvas stage: don't
clamp height and width independently when they need to match.
